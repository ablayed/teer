# Zod 3 : bornes existantes vérifiées avant les éléments

12 novembre 2026. Plan avant code : conserver Zod 3.25.76 et tous les seuils métier existants ; introduire un préprocesseur pur qui rejette une taille excessive avant ZodArray._parse ; appliquer seulement aux cinq tableaux déjà plafonnés (raisons d'annulation 5, trois paniers 20, composition 50). Même message de taille et mêmes entrées valides. Aucun maximum inventé pour achats ou allocations de cash, aucune troncature, aucune migration ni configuration distante.

Tests fonctionnels bornés : trois éléments seulement pour vérifier que la porte ne parcourt pas les éléments au-delà d'un maximum de deux ; message et chemin comparés au validateur Zod 3 natif, cas positifs, minimum, type incorrect et chemin async. Puis sanity complète et revue de chaque schéma/caller. Aucun payload de déni de service ou test d'exploitation.

Contexte : GHSA-mrhx-c7xc-m3w5 reste actif alors que CVE-2023-54404 est rejetée depuis le 28 octobre. Le code v3 installé continue de parcourir les éléments après son contrôle max ; la présente barrière réduit ce travail sur les champs déjà bornés. Elle ne corrige pas toute collection interne d'une dépendance ni les parseurs JSON et résultats SQL déjà alloués. Rapport complet dans security-audit-proofs/docs/security/securite-3-zod-risk.md. Le candidat Zod 4/UUID reste isolé.

Risques UX : aucune nouvelle limite ; les entrées trop longues reçoivent d'abord le message de taille, sans accumuler les erreurs individuelles. Cette réduction de détails sur les seuls inputs invalides est intentionnelle. Les tableaux légitimes, transformations des éléments, minimums et types restent ceux du schéma original. Retour arrière sans migration : rétablir le commit dans une PR relue réintroduirait le parcours après dépassement.

Limites et verdict : ce durcissement ne fait pas disparaître l'alerte pnpm de version ni ne démontre l'impossibilité d'un épuisement mémoire. Deux collections d'entrée sans maximum et deux tableaux de résultat SQL restent à borner après revue des volumes métier. Aucun statut global VERIFIED SECURE ; NO-GO maintenu. Fusion seulement si les critères de compatibilité et les deux CI initiales du SHA final sont satisfaits ; ne pas déclarer le GHSA fermé par cette seule barrière.

Validation locale exécutée : six tests du helper verts, dont zéro élément validé après rejet d'une liste de trois valeurs ordinaires ; typecheck/lint/build et invariants ACL/service-role verts ; 2 071 unités passantes, trois ignorées préexistantes ; 812 RLS passantes. Matrice HTTP/RLS réelle sur ce build avec Redis local et fournisseur simulé : 1 046 observations attendues, zéro violation observée, 828 contrôles étayés et 218 indéterminés selon le classificateur corrigé de M1. L'autorisation n'est pas certifiée pour les indéterminés. Les tests existants sont inchangés ; package.json et pnpm-lock.yaml aussi. Journaux `security-audit-proofs/docs/security/evidence/s3-zod3-bounds-*`.

Revue : le préprocesseur rejette uniquement, ne transforme pas l'entrée et conserve les types d'entrée/sortie du tableau original. Le schéma natif conserve minimum et validation des éléments pour les entrées sous la limite. Les cinq substitutions réutilisent exactement 5, 20 et 50 ; aucune limite d'infrastructure ou de consommation monétaire ajoutée. Aucun nouvel appel réseau. La revue du risque global reste dans le rapport Zod, pas déduite de cette PR compatible.
