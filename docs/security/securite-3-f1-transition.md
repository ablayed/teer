# SEC-D-001 — arrêt au plan de transition, option E écartée

12 novembre 2026. PR #314 diagnostique non fusionnée ; aucune nouvelle reproduction, migration ni modification d'abonnement. Le diagnostic A/B/C/D de securite-2-f1-diagnostic.md reste applicable aux chemins du code inspectés. La fusion F1 exige une nouvelle approbation.

Le domaine de X-Shopify-Shop-Domain n'est pas signé comme partie du corps HMAC et reste un indice. Un 401/403 Admin API peut résulter d'un jeton expiré, révoqué, d'une réautorisation ou d'un autre problème ; même un refus de refresh n'authentifie pas l'événement comme désinstallation de cette boutique. Une disponibilité réseau ou une réponse de quota ne doit pas décider d'un effet destructif. Aucun appel synchrone de vérification réseau n'est ajouté ; l'option E ne devient pas une barrière d'autorisation. L'allowlist IP déclarée vérifiée par le porteur ne change pas cette conclusion d'identité.

## Priorités de transition

1. Payload signé : lorsque le domaine est présent et conforme, le comparer à l'identité attendue ; cela ne résout pas les payloads légitimes avec domain/myshopify_domain null. Ne pas convertir ces derniers en rejets systématiques.
2. Shop ID : le sample officiel porte un id numérique ; ne pas déduire la présence universelle de ce seul exemple. Lors d'OAuth authentifié, lire shop.id et myshopifyDomain via le jeton de cette installation, vérifier l'identité et persister shop_gid avec les mêmes protections de bail/fencing que les credentials. Aujourd'hui le champ n'est pas alimenté. Pour les installations existantes, prévoir lecture authentifiée bornée et traçable ou réautorisation ; aucun backfill distant autorisé ici. Une donnée absente ne peut pas être inventée à partir d'un header.
3. Ingest par installation : le routage opaque existant établit une installation avant traitement. Vérifier la validation du token, l'app liée et le HMAC du corps avant réservation. Cette voie ne transforme pas les anciennes livraisons globales en livraisons authentifiées par installation.
4. E11 : inventorier par installation active les topics et l'état réellement présent chez Shopify ; réparer les abonnements manquants dans un lot autorisé, prouver la reprise d'événements et l'idempotence, faire un canary désinstallation/réinstallation sur boutique dédiée, puis seulement retirer le global par une version Shopify explicitement approuvée. Conserver la possibilité de retour contrôlé sans réactiver un routage destructif non authentifié.

Les validations d'identité doivent précéder webhook_event, déduplication et toute écriture/journalisation tenant. Le code historique actuel ne respecte pas cette séquence : lookup privilégié par header, attribution puis réservation précèdent une identité fiable. Ne pas ajouter de log tenant prétendument authentifié pendant la vérification ; une alerte de sécurité globale éventuelle ne doit contenir ni domaine réel, secret, corps client ni token.
